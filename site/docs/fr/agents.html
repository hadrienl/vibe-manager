Agents, relances et fermeture de l’app

Changez d’agent ou de modèle sans perdre le travail, remettez au travail une session fermée, et quittez sans interrompre un agent au milieu de son tour.

Agents pris en charge

Vibe Manager fait tourner Claude Code et Codex CLI, chacun dans sa propre interface de terminal, avec votre compte et votre configuration. Il ne passe aucune option qui réduise les permissions réglées pour votre CLI, et ne lit aucun identifiant de leur compte. La seule clé qu’il connaisse est celle d’un endpoint que vous avez déclaré vous-même. Ce qu’un agent a le droit de faire dans une session relève de sa propre configuration : Vibe Manager ne l’élargit ni ne la restreint.

Deux ajouts sont faits au lancement, pour ce lancement seulement : les hooks de l’agent signalent son activité — il travaille, attend, a terminé — une fois que vous les avez approuvés (Réglages › Agents), et son serveur d’outils vibe-browser lui donne la vue web.

Agents sur un endpoint

Un endpoint est un serveur de modèles joignable en HTTP : sur ce Mac (Ollama, LM Studio) ou dans le cloud (OpenRouter, la passerelle de votre entreprise). Ses modèles apparaissent à côté de Claude Code et de Codex quand vous créez une session, et la session fait tourner Claude Code ou Codex sur eux : même terminal, même vue conversation, mêmes demandes, même reprise après une relance.

  1. Réglages › Endpoints › Ajouter un endpoint…, puis un point de départ : Ollama, LM Studio, OpenRouter, ou un Autre serveur. Un serveur connu remplit l’adresse, le protocole et la clé attendue.
  2. Clé : saisie une fois, écrite dans le trousseau de session (un élément par endpoint, jamais synchronisé) et plus jamais affichée. Supprimer l’endpoint la supprime.
  3. Modèles : Lire depuis l’endpoint liste ce que le serveur propose. Un modèle qui ne sait pas appeler d’outils est gardé mais pas proposé : sans outils, un agent ne lit aucun fichier. Donnez à chaque modèle sa vraie fenêtre de contexte.
  4. Piloté par : Automatique choisit Claude Code ou Codex selon le protocole du serveur ; vous pouvez imposer l’un ou l’autre.
  5. Tester envoie une courte requête qui demande au modèle d’appeler un outil, et dit ce qui a marché : joignable, authentification, réponse en flux et vitesse, appel d’outil, réponse après l’outil, jetons comptés. Un endpoint dont le dernier test a échoué n’est plus proposé pour une nouvelle session.

Un serveur qui ne suit aucun standard se décrit avec le protocole Personnalisé, dans un document JSON : Insérer l’exemple en donne un pour commencer. Le format est détaillé dans docs/endpoints.md.

Changer d’agent ou de modèle

Session › Changer d’agent… (⌃⌘M), ou Changer… dans la section Agent de l’inspecteur, change l’agent ou le modèle d’une session.

Le nouvel agent reçoit un résumé que vous pouvez lire et modifier d’abord.
  • Un autre modèle du même agent reprend la même conversation et n’envoie rien.
  • Un autre agent démarre une nouvelle conversation, avec un résumé de la session : qui y a travaillé, où en est le travail sur chaque branche et chaque worktree, ses notes et le prompt avec lequel elle a été créée. Le résumé est affiché et modifiable avant l’envoi, et n’est jamais présenté comme la conversation elle-même.

Rien n’est arrêté avant que vous confirmiez avec Arrêter et changer (⌘Return). Si le nouvel agent ne démarre pas, la session revient à son agent précédent, qu’on peut reprendre comme avant. Chaque changement est conservé dans l’historique de la session, et la vue conversation continue de lire les transcripts de tous les agents qu’a eus la session.

Relancer une session fermée

Une session fermée affiche une barre : « Cette session est fermée. Tout ce qu’elle contient est conservé. » Relancer — ou Session › Relancer la session, ⌃⌘R — la remet au travail avec le même agent, le même modèle, le même dossier et le même worktree.

Une session fermée garde tout, et se relance en une commande.
  • Quand l’agent peut reprendre sa propre conversation, il le fait, et rien ne lui est envoyé.
  • Quand il ne le peut pas — aucun identifiant n’a jamais été conservé, ou la CLI le refuserait —, l’app le signale et propose un nouveau processus avec un résumé de la session, affiché et modifiable avant l’envoi.

Une session créée avec Ajouter à À faire n’a jamais tourné : la même commande s’intitule alors Démarrer la session.

Quitter sans arrêter les agents

Chaque terminal tourne dans un hôte des terminaux, un processus d’arrière-plan sans fenêtre ni icône dans le Dock. Aussi, quand des agents travaillent et que vous quittez, Vibe Manager demande :

Laisser tourner
Les agents poursuivent leur tour. Au lancement suivant, chacun réapparaît à l’écran tel qu’il était, rien n’est relancé ni envoyé ; celui qui a terminé entre-temps montre sa dernière sortie. Les terminaux annexes continuent eux aussi de tourner.
Tout arrêter
Les agents sont arrêtés, avec l’intention de les reprendre : au lancement suivant, ils reviennent grâce à la reprise de leur propre CLI, sans rien demander.

Cochez Ne plus demander, ou faites votre choix dans Réglages › Général, pour toujours faire de même. Les mises à jour suivent le même choix : une mise à jour peut s’installer pendant que les agents continuent de tourner.

Redémarrer le Mac ou fermer la session utilisateur arrête les agents : Laisser tourner survit à l’app, pas à votre session macOS. Au lancement suivant, les sessions sont reprises nativement.

Après un plantage

Un plantage n’est pas une intention : au lancement suivant, un bandeau propose Reprendre les sessions ou Ignorer, au lieu de les reprendre de lui-même. Les sessions reviennent une par une, avec une progression et un moyen d’annuler ; une restauration qui enverrait un texte à un agent n’est jamais automatique.

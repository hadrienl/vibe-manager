# 0022 — The agent's activity, reported by its own hooks

- Status: accepted
- Date: 2026-09-25
- Issue: [#45](https://github.com/hadrienl/vibe-manager/issues/45)

## Context

The sidebar said "Running" for every session whose process was alive, which is every session it
lists. What the user needs to know at a glance is what the agent is doing: waiting for an
instruction, working, or waiting for them — a question, a permission, an answer they have not read.

The terminal alone cannot tell. Reading the TUI's screen would tie the application to the drawing
of two interfaces that change every week, and #40 and #38 refused it for the same reason. Both CLIs
can run programs of the user's choosing at known moments — hooks — and hand them what happened as
JSON: that is the structured signal this ADR builds on.

## Decisions

### A log per session, not a socket

The hooks append one line to `AgentActivity/<session id>.log`, in the data folder (`0700`, files
`0600`), named to the agent in `VIBE_AGENT_ACTIVITY_LOG`. A line is `event ⇥ seconds ⇥ payload`.

A socket to the application was rejected: since ADR 0017 an agent can outlive the application, and
a turn that finishes while nobody listens is precisely the one that must come back as unread. An
append never blocks the hook, depends on nothing being alive, and is read back at the next launch
from where the last reading stopped (`agent-activity.json` keeps the offset and the file's inode).
The terminal host stays a carrier of terminal bytes.

The application never truncates a log a hook may be writing to. It removes it when a new process
starts for the session, and past 1 MiB, once everything has been read, renames it aside, reads
whatever a hook still wrote into it, and drops it; the next hook creates the file again.

### The hook is written out, and says nothing

Every hook runs the same `/bin/sh -c '…' vibe-activity <event> <keep|drop|match>`, generated by
`AgentActivityHookCommand`. No script is installed, so nothing breaks when the application is moved
or updated while an agent runs. It reads its input to the end in every case (a CLI writing to a
closed pipe would report an error), writes nothing on its output (a `PermissionRequest` hook that
answered would decide in the user's place), and always exits 0.

Only what the next features need is kept: the payload of questions and permissions (for #40), of
`SessionStart` (the transcript path) and of `Notification`. A prompt's text and a tool's output —
possibly megabytes — are dropped by the hook itself; for `UserPromptSubmit`, only whether the
prompt is the `<task-notification>` a background task sends is written back.

### Injected at each launch, never installed

Claude Code gets its hooks with `--settings '<json>'`, which adds to the user's own settings rather
than replacing them (verified against 2.1.282: the user's hooks still run). Codex gets
`-c 'hooks.<Event>=[…]'`. Neither `~/.claude/settings.json` nor `~/.codex/hooks.json` is touched,
and a CLI started outside Vibe Manager is not affected. Codex's `notify` is not used: it holds one
program, and the user may already have one.

### Codex approves hooks; Vibe Manager asks first

Codex runs a hook only once the user has approved it, and remembers the approval in
`config.toml` as `hooks.state."<key>".trusted_hash`, keyed by the hook's event and place
(`/<session-flags>/config.toml:stop:0:0`) and by the fingerprint of its definition. A hook it does
not know opens a full-screen review before anything else. `-c 'hooks.state…'` is ignored — a hook
cannot approve itself — and `bypass_hook_trust=true` would skip the review for every hook, those of
a cloned repository included: rejected.

Vibe Manager asks in its own words instead, once, before the first Codex launch that needs it. On
yes, it asks Codex's local server (`codex app-server`, `hooks/list`) which hooks are pending, keeps
only those whose command is ours byte for byte, and writes their approval with `config/batchWrite`
— the method Codex's own interface uses, which leaves the rest of the file, comments included, as
it was — then asks again to confirm. The approval is remembered by a fingerprint of the CLI, its
version and the hooks, so later launches ask nothing. On no, Codex's agents run without hooks, and
the Settings can change that. If the server cannot be asked, the agent is launched with its hooks
and Codex asks for itself.

### Interruptions come from the transcript

Claude Code reports no interruption through its hooks: Escape during a turn and a permission refused
with it leave no event at all (verified). It does write `[Request interrupted by user]` — or
`… for tool use]` — as a user message in the transcript its `SessionStart` names. That line is read,
in that exact shape only (a tool's output that quotes the words is not one). Escape and Control-C
typed in the session also end the turn at once, and Claude's `idle_prompt` notification, a minute
later, catches anything else. No silence timer is used for agents with hooks: how often a TUI
redraws is guaranteed nowhere. Codex has an `Interrupt` hook.

### Answering from the terminal

After a permission is granted, the CLIs say nothing until the tool ends, so the keystroke that
answers is read: Enter or a digit for Claude Code, `y`, `a`, `n` or Enter for Codex, each provider
declaring its own. Only for permissions: a question can be answered in free text, whose first letter
must not count as the answer, and its own signal arrives at once. Whatever the agent says next
confirms or corrects it.

### The machine is pure

`AgentActivityMachine` holds every rule, and is tested without a disk, a process or a clock.
`TrackAgentActivity` feeds it — the log, the terminal's output, the keystrokes, which session is
visible — and publishes the states that the sidebar, and later #40 and #38, read. A launch whose
hooks have not spoken within ten seconds (hooks disabled by the user or by a policy) falls back on
the output: working while it writes, idle after three silent seconds, and never a question or an
unread answer that nothing reported.

### Unread

An answer is unread when its turn ended while its session was not visible — selected, with the
application active and its window shown. Showing the session reads it; writing to the agent reads
it too, but a background task resuming the agent does not. The mark survives a relaunch, and a
native resume (#11); closing or archiving the session drops it.

## Consequences

- A process of the same user can write false lines into a log. The consequence is a wrong symbol;
  it can neither read a terminal nor act on an agent.
- Each hook costs a shell, about 10 ms, on the path of the event: once per prompt, per turn, per
  question, and per tool for `PostToolUse`.
- Changing a Codex hook's command is a deliberate change: every user is asked again, once.
- The transcript marker is Claude Code's convention, not an interface. Fixtures pin both forms; if
  it disappears, the keystrokes and `idle_prompt` remain.
